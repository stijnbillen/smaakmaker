# T-004 — R-017: Beheerder

Afhankelijk van T-003 (tabel `invites`, `profiles`, aanmelden, `AuthProvider`, `formatDate`).

## Wat

Eén of meer gebruikers zijn beheerder. Dat stel je in de databank in, niet in de app. Een beheerder maakt op het scherm "Uitnodigingen" codes aan en ziet per code de status, de gebruiker en de vervaldatum. Daarnaast mag een beheerder elk recept (en later elke review) verwijderen. Een gewone gebruiker mag alleen de eigen inhoud verwijderen, en dat dwingt de databank af.

## Acceptatiecriteria

1. **Alleen een beheerder ziet en gebruikt het scherm "Uitnodigingen". Een gewone gebruiker krijgt via de databank-API een weigering.**
   - *Databank (Vitest, lokale Supabase):* een gewone gebruiker roept `rpc('list_invites')` en `rpc('create_invite')` aan. Beide geven een fout met code `42501` en er komt geen rij bij in `invites` (controle met de service-client). Ook `select` en `insert` rechtstreeks op `invites` worden geweigerd (`permission denied`). Met alleen de publieke sleutel (anon) gebeurt hetzelfde.
   - *Databank:* een beheerder roept dezelfde functies aan en dat lukt.
   - *Interface (Playwright, 360 × 640):* een beheerder ziet op Profiel de link "Uitnodigingen" en opent het scherm `/uitnodigingen`. Een gewone gebruiker ziet de link niet. Opent hij `/uitnodigingen` rechtstreeks, dan komt hij op `/profiel` en wordt geen code getoond.
2. **Een beheerder maakt een code aan en ziet per code de status (open, gebruikt, verlopen), de gebruiker en de vervaldatum.**
   - *Databank:* `create_invite()` geeft een code terug die voldoet aan `^[ABCDEFGHJKMNPQRSTUVWXYZ23456789]{10}$`. `check_invite` zegt voor die code `true`. 50 aanroepen geven 50 verschillende codes.
   - *Databank:* de pure functie `invite_status(created_at, used_at, at)` geeft `open` bij `at = created_at + 7 days`, `verlopen` één seconde later en `gebruikt` zodra `used_at` gevuld is (ook als de code daarna zou verlopen). Dezelfde 7-dagengrens als `invite_is_valid_at`.
   - *Databank:* `list_invites()` geeft per code `code`, `status`, `used_by_name` (weergavenaam van de gebruiker, alleen bij `gebruikt`), `expires_at` (= `created_at + 7 days`) en `created_at`, nieuwste eerst. Een code die een testgebruiker verbruikt heeft, staat op `gebruikt` met diens naam. Een code waarvan de test `created_at` meer dan 7 dagen terugzet, staat op `verlopen`.
   - *Interface:* de beheerder tikt op "Nieuwe code". De nieuwe code staat bovenaan met "Open" en een vervaldatum ("vervalt op 9 november 2026 om 14:05"). Vooraf klaargezette codes tonen "Gebruikt" met de naam van de gebruiker en "Verlopen". Zonder codes staat er "Nog geen uitnodigingen." (`ListState`), en tijdens het laden de laadtoestand.
   - *Unit (Vitest):* `formatDateTime` geeft voor `2026-11-09T13:05:00Z` "9 november 2026 om 14:05" (Europe/Brussels).
3. **Een beheerder kan elk recept en elke review verwijderen (met bevestiging). Een gewone gebruiker alleen de eigen.**
   - *Databank:* gebruiker A verwijdert zijn eigen recept en dat lukt. Gebruiker B probeert het recept van A te verwijderen: er wordt niets verwijderd (0 rijen) en het recept bestaat nog (controle met de service-client). Een beheerder verwijdert het recept van B en dat lukt.
   - *Unit:* `canDelete({ authorId }, { userId, isAdmin })` is waar voor de auteur en voor een beheerder, en onwaar voor anderen.
   - *Reviews en de knop met bevestiging:* de tabel voor reviews en de detailpagina bestaan nog niet. Deze taak levert `is_admin()` en de regel "auteur of beheerder" voor recepten. De taken van R-003 (detailpagina, knop "Verwijderen" met bevestiging) en R-012 (reviews) gebruiken `is_admin()` en `canDelete` en testen daar de bevestiging in de interface. Zie Risico's.
4. **De eerste beheerder wordt buiten de app ingesteld, met een databankinstelling, niet via een publiek scherm.**
   - *Databank:* een gewone gebruiker kan zichzelf geen beheerder maken. `insert` in `admins` wordt geweigerd. `rpc('grant_admin')` wordt geweigerd voor `anon` en `authenticated`.
   - *Databank:* `select public.grant_admin('<e-mailadres>')` via de directe Postgres-verbinding (`tests/helpers/pg.ts`, alleen lokaal) maakt die gebruiker beheerder. Daarna lukt `list_invites()` voor hem. Een onbekend adres geeft een fout.
   - *Interface:* geen enkele route in de app maakt iemand beheerder. De routelijst bevat geen beheerdersinstelling, en `src/` roept `grant_admin` nergens aan (controle met een tekstzoektest op `src/`).
   - *Documentatie:* `docs/beheer.md` beschrijft de SQL voor de eerste uitnodigingscode en de eerste beheerder.

Daarnaast, uit R-001 en R-016: `/uitnodigingen` komt in `tests/e2e/routes.ts` met een beheerderssessie. De controles op 360 px, tikdoelen (ook de kopieerknop en "Nieuwe code"), labels, focus en lijsttoestanden gelden ook voor dat scherm.

## Plan

In deze volgorde:

1. **`supabase/migrations/<ts>_admins.sql`** (nieuw)
   - Tabel `admins (user_id uuid primary key references public.profiles(id) on delete cascade, created_at)`. RLS staat aan, zonder policies, en `revoke all` voor `anon` en `authenticated`.
   - `is_admin() returns boolean`: `security definer`, `stable`, `search_path = ''`, geeft `exists (select 1 from admins where user_id = auth.uid())`. `execute` alleen voor `authenticated`.
   - `grant_admin(p_email text)`: `security definer`, zoekt de gebruiker in `auth.users` en voegt hem toe aan `admins` (`on conflict do nothing`). Een onbekend adres geeft een exception. `revoke all` voor `public`, `anon` en `authenticated`, dus alleen bruikbaar met SQL (SQL-editor of `psql`).
   - `generate_invite_code()`: 10 tekens uit `ABCDEFGHJKMNPQRSTUVWXYZ23456789`, gemaakt met `extensions.gen_random_bytes`. Niet uitvoerbaar voor de client.
   - `invite_status(created_at, used_at, at) returns text` (`open` / `gebruikt` / `verlopen`). Een pure functie, met dezelfde grens als `invite_is_valid_at`.
   - `create_invite()`: `security definer`. Geen beheerder, dan `raise exception … using errcode = '42501'`. Anders `insert` met een gegenereerde code en `created_by = auth.uid()`. Bij een botsing op `unique` opnieuw proberen. Geeft dezelfde vorm terug als een rij van `list_invites`.
   - `list_invites()`: `security definer` met dezelfde controle. Geeft `code`, `status`, `used_by_name` (join op `profiles`), `expires_at`, `created_at`, gesorteerd op `created_at desc`.
   - `invites` blijft dicht: geen grants en geen policies erbij.
   - `recipes`: `grant delete on public.recipes to authenticated` en de policy `recipes delete by author or admin` met `using (author_id = auth.uid() or public.is_admin())`.

## Kernbeslissingen

- **Rechten in rij-niveau-regels, niet alleen in de interface:**
  - De beheerdersrol staat in een tabel `admins` die de client niet kan lezen of schrijven.
  - Elke beheerdersfunctie controleert `is_admin()` in de databank zelf.
  - Verwijderen van recepten loopt via een RLS-policy ("auteur of beheerder").
  - De link en de routebewaking in de interface zijn alleen gemak, geen beveiliging.
- **Een recept wijzigt alleen de auteur; een beheerder kan alles verwijderen:** de policy geeft de beheerder alleen `delete`, geen `update`. Wijzigen blijft voor de auteur (R-003).
- **Alle zichtbare teksten in `nl.json`:** statuslabels, knoppen, de lege toestand en de datumtekst. De databank geeft de status als sleutelwaarde (`open`, `gebruikt`, `verlopen`); de interface vertaalt die via `nl.json`.
- **Geen geheime sleutels in de client:**
  - Beheerder worden kan alleen met SQL (`grant_admin`, niet uitvoerbaar voor `anon` en `authenticated`).
  - De client gebruikt alleen de publieke sleutel.
  - `docs/beheer.md` gebruikt de SQL-editor of `psql`, niet de service-sleutel in de app.
- **Tests tegen lokale Supabase:** `grant_admin` wordt getest via de lokale Postgres-verbinding (poort 54322) uit `tests/helpers/pg.ts`, nooit tegen de cloud.
- **Mobiel eerst, 360 px:**
  - Codes zijn 10 tekens in een vast lettertype. Ze moeten zonder horizontaal scrollen passen.
  - "Nieuwe code" en "Kopieer" zijn ≥ 44 × 44 px.
- **Tokens en `frontend-design`-skill:** geen vaste kleurwaarden. Statuslabels gebruiken bestaande kleurtokens, of nieuwe tokens volgens de naamgeving uit `docs/beslissingen.md`, zodat de contrasttest ze controleert.

## Risico's

- **Criterium 3 is in deze taak maar deels zichtbaar:**
  - Recepten verwijderen kan nog nergens in de interface, want er is geen detailpagina.
  - Reviews bestaan nog niet.
  - Deze taak legt de rechten in de databank vast en test ze. De knop met bevestiging (en dat het recept uit het overzicht verdwijnt) hoort bij R-003; de policy "auteur of beheerder" voor reviews bij R-012.
  - Die taken moeten `is_admin()` gebruiken in plaats van een eigen controle.
- **Foto's van andermans recept:** R-005 zegt dat het verwijderen van een recept ook de bestanden verwijdert. De opslagregels (storage policies) moeten dan ook de beheerder toelaten, anders blijven foto's achter als een beheerder een recept wist. Dat hoort bij R-005.
- **Varianten:** verwijdert een beheerder een bronrecept, dan moet de variant blijven bestaan (R-006). De koppeling (`on delete set null`) hoort bij die taak. Deze policy mag dat niet blokkeren.
- **Stille weigering bij verwijderen:** RLS geeft bij `delete` op andermans recept geen fout maar 0 rijen. De test controleert daarom of de rij nog bestaat. De interface (R-003) moet 0 rijen als mislukking behandelen.
- **Raden van codes:** `check_invite` is publiek. 10 tekens uit 31 symbolen geven ongeveer 8 × 10¹⁴ mogelijkheden, wat met de bestaande snelheidslimieten van de API niet haalbaar is om te raden. Een eigen limiet op `check_invite` valt buiten deze taak.
- **Hoofdletters:** codes zijn hoofdletters, maar een gebruiker typt ze op een gsm misschien in kleine letters. De client zet de invoer daarom om naar hoofdletters. Oude testcodes met kleine letters blijven werken als de testhulp ook hoofdletters gebruikt. De tester controleert de bestaande auth-tests.
- **Trigger op `invites`:** de opruimtrigger loopt alleen bij `update` (verbruik). `create_invite` voegt in en raakt die trigger niet. Het terugzetten van `created_at` in de test is een `update`, die zo een onbevestigde testgebruiker met die code kan opruimen. Dat is bedoeld gedrag, maar de test moet er rekening mee houden.
- **Opengelaten door de requirement, zelf ingevuld** (in `docs/beslissingen.md`):
  - Extra beheerders worden ook via SQL ingesteld. Er is geen scherm om iemand beheerder te maken, want geen criterium vraagt erom.
  - Een beheerder kan een open code niet intrekken of verwijderen.
  - De link naar "Uitnodigingen" staat op Profiel, omdat de navigatie precies vier ingangen houdt (R-016).
  - Een gewone gebruiker op `/uitnodigingen` gaat naar `/profiel`.
  - Een code die nog aan een onbevestigde gebruiker hangt, telt als "Open" tot de bevestiging.
  - De vervaldatum toont datum en uur, omdat de grens op de seconde ligt.
  - Codes zijn 10 tekens, zonder verwarrende tekens (0/O, 1/I/L).
