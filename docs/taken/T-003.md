# T-003 — R-002: Aanmelden met uitnodigingscode

Afhankelijk van T-001 (projectbasis, lokale Supabase) en T-002 (navigatie, stijl, `AppLayout`).

Beslissing van de eigenaar (`VRAGEN.md`, T-003, beantwoord 2026-11-01): **optie 2**. Dezelfde mail bevat de inloglink én een code van 6 cijfers. Het aanmeldscherm krijgt een veld "Code uit de e-mail".

## Wat

Alleen wie een geldige uitnodigingscode heeft (eenmalig, 7 dagen geldig), kan een account maken. De databank dwingt dat af. Aanmelden gebeurt zonder wachtwoord: de mail bevat een inloglink én een code van 6 cijfers. Daarna kiest de gebruiker bij het eerste aanmelden een weergavenaam, en die naam en de datum staan bij elk recept.

## Acceptatiecriteria

1. **Zonder geldige uitnodigingscode geen account. Een ongeldige of gebruikte code geeft "Deze code is niet geldig."**
   - *Databank (Vitest, lokale Supabase):* `auth.signInWithOtp` met een onbekende code, met een gebruikte code of zonder code in `options.data.invite_code` maakt geen rij in `auth.users` (controle met de service-client). Hetzelfde geldt voor `auth.admin.createUser` zonder geldige code: de trigger weigert die ook.
   - *Databank:* met een geldige code ontstaat de gebruiker, en na bevestiging staat de code op gebruikt (`used_by` = id van de nieuwe gebruiker).
   - *Interface (Playwright):* in de modus "Nieuw account" een verzonnen code en daarna een gebruikte code invullen, telkens met de tekst "Deze code is niet geldig." bij het codeveld. Er wordt geen mail verstuurd (de Mailpit-inbox blijft leeg).
2. **Een code is eenmalig en vervalt 7 dagen na aanmaken. Op exact 7 × 24 uur is ze nog geldig, 1 seconde later niet.**
   - *Databank:* de pure functie `public.invite_is_valid_at(code, at timestamptz)` geeft `true` voor `at = created_at + 7 days` en `false` voor `at = created_at + 7 days + 1 second`. Zo hangt de grens niet af van de klok tijdens de test.
   - *Databank:* een code met `created_at` = `now() - 7 days - 1 second` (gezet via de service-client) wordt bij aanmaken van een account geweigerd.
   - *Databank:* twee aanvragen met dezelfde code voor twee adressen. Wie eerst bevestigt, krijgt het account. De bevestiging van de tweede faalt, en die gebruiker blijft zonder sessie.
3. **Bij het eerste aanmelden geeft de gebruiker een weergavenaam van 2 tot 40 tekens. 1 of 41 tekens wordt geweigerd.**
   - *Databank:* `update profiles set display_name` met 1 of 41 tekens geeft een check-fout. Met 2 en 40 tekens lukt het. Tekens tellen na weghalen van spaties vooraan en achteraan, met `char_length`.
   - *Interface:* een nieuwe gebruiker zonder naam komt na het aanmelden op `/welkom`. Met 1 of 41 tekens verschijnt een melding bij het veld en blijft de gebruiker op `/welkom`. Met 2 tekens komt hij op "Recepten".
   - *Interface:* een gebruiker die al een naam heeft, ziet `/welkom` niet meer.
4. **Een ongeldig e-mailadres wordt geweigerd met een melding bij het veld.**
   - *Unit (Vitest):* `isValidEmail` voor een reeks goede en foute adressen (`a@b.be` goed; `a@b`, `a b@c.be`, `@c.be` en een lege waarde fout).
   - *Interface:* "Stuur mij een code" met `piet@` toont de melding bij het e-mailveld (`aria-invalid="true"`, gekoppeld met `aria-describedby`). Er wordt geen verzoek naar `/auth/v1/otp` gestuurd.
5. **Zonder aanmelding zijn recepten, reviews en foto's niet leesbaar of schrijfbaar, ook niet rechtstreeks via de databank-API.**
   - *Databank:* met alleen de publieke sleutel geeft `select` op `recipes` en `profiles` niets of een weigering, en `insert` in `recipes` wordt geweigerd. `invites` is voor de anonieme rol volledig dicht. Reviews en foto's bestaan nog niet; hun taken herhalen deze controle met dezelfde test als patroon.
   - *Interface:* `/`, `/nieuw`, `/favorieten` en `/profiel` zonder sessie sturen door naar `/aanmelden`.
6. **De mail bevat de inloglink én een code van 6 cijfers. Het aanmeldscherm heeft een veld "Code uit de e-mail". Een juiste code meldt aan; een foute of verlopen code geeft "Deze code is niet geldig." en meldt niet aan.**
   - *Databank/mail:* na `signInWithOtp` haalt de testhulp de mail op uit Mailpit (lokale Supabase). De tekst bevat een link naar `/auth/v1/verify` en precies één code van 6 cijfers (`\b\d{6}\b`). Dat geldt voor een nieuwe gebruiker (bevestigingsmail) en voor een bestaande gebruiker (inloglinkmail).
   - *Interface:* de code uit Mailpit invullen in "Code uit de e-mail" brengt de gebruiker naar "Recepten" (of naar `/welkom` als hij nog geen naam heeft).
   - *Interface:* een foute code, bijvoorbeeld de juiste code met het laatste cijfer gewijzigd, geeft "Deze code is niet geldig.". Er staat dan geen sessie in `localStorage` en de gebruiker blijft op `/aanmelden`.
   - *Interface:* een verlopen code. De test zet het verzendtijdstip van de code in de databank meer dan `otp_expiry` terug, via een directe Postgres-verbinding op poort 54322 met alleen de lokale gegevens. Daarna geeft de code "Deze code is niet geldig.".
   - *Interface:* de inloglink uit de mail openen in een nieuwe browsercontext meldt daar aan. Zo werkt de link ook in een andere browser dan waarin de mail werd aangevraagd.
7. **Een gebruiker kan afmelden; daarna toont de app het aanmeldscherm.**
   - *Interface:* Profiel, dan "Afmelden": de URL wordt `/aanmelden`, de sessie-sleutel in `localStorage` is weg, en terug naar `/` blijft op `/aanmelden` uitkomen.
8. **Elk recept en elke review toont de weergavenaam van de auteur en de datum.**
   - *Interface:* gebruiker A ("Annemie") maakt een recept. Gebruiker B ziet in het overzicht bij dat recept "Annemie" en de datum in het Nederlands (bv. "1 november 2026").
   - *Unit:* `formatDate` geeft voor `2026-11-01T10:00:00Z` "1 november 2026" (tijdzone Europe/Brussels vast in de test).
   - Reviews en de detailpagina bestaan nog niet. Hun taken gebruiken dezelfde component `AuthorLine`.

Daarnaast, uit R-001 en R-016: `/aanmelden` en `/welkom` komen in `tests/e2e/routes.ts`, maar zonder sessie. De 360 px-controle, de tikdoelen, de labels en de focuscontrole gelden ook voor die schermen.

## Kernbeslissingen

- **Aanmelden met inloglink, geen wachtwoord:** de inloglink blijft bestaan. De 6-cijferige code komt erbij, zoals de eigenaar koos, uit dezelfde mail van Supabase Auth. Er komt geen wachtwoord en geen extra dienst. De client gebruikt de impliciete flow (de standaard van supabase-js), geen PKCE. Met PKCE werkt een link alleen in de browser die de mail aanvroeg; zo werkt de link ook in Safari terwijl de code de geïnstalleerde app bedient.
- **Rechten in rij-niveau-regels, niet alleen in de interface:**
  - De controle op de uitnodigingscode zit in een trigger op `auth.users`, zodat ook een rechtstreekse API-aanroep zonder code geen account oplevert.
  - Het verbruik van de code is atomisch bij de bevestiging.
  - `invites` is dicht voor de client. `profiles` mag alleen de eigenaar wijzigen, en alleen de kolom `display_name`.
  - De lengte van de naam staat als check in de databank.
  - Elke invoer wordt ook in de databank gevalideerd.
- **Alle zichtbare teksten in `nl.json`:** dat geldt ook voor de mailteksten. Supabase leest de templates als HTML-bestand, maar ze worden uit `nl.json` gegenereerd en een test bewaakt dat.
- **Geen geheime sleutels in de client:** de client gebruikt alleen de publieke sleutel. `check_invite` is een smalle `security definer`-functie die alleen ja of nee geeft. De service-sleutel en de Postgres-verbinding staan alleen in `tests/helpers/`.
- **Tests tegen lokale Supabase:** de mail komt uit lokale Mailpit en Postgres draait lokaal op poort 54322. De bestaande localhost-controle blijft gelden.
- **Mobiel eerst, 360 px:**
  - Het codeveld krijgt `inputmode="numeric"` en `autocomplete="one-time-code"`, zodat iOS en Android de code uit de mail kunnen voorstellen.
  - De tikdoelen zijn ≥ 44 px.
  - De nieuwe schermen staan in de routelijst.
- **`frontend-design`-skill en tokens:** de nieuwe schermen gebruiken alleen bestaande tokens uit `tokens.css`. Het aanmeldscherm is het eerste wat een gebruiker ziet en krijgt de stijl "warme keuken".

## Risico's

- **Wanneer Supabase de gebruiker aanmaakt:** `signInWithOtp` maakt de rij in `auth.users` al bij het versturen, niet pas bij bevestiging. Daarom controleert de trigger de code bij `insert`, maar verbruikt hij ze pas bij `email_confirmed_at`. Een tikfout in het e-mailadres verbrandt de code dus niet. Te controleren in de test: zet `verifyOtp` (en de inloglink) bij een nieuwe gebruiker echt `email_confirmed_at`, ook met `enable_confirmations = false`? Zo niet, dan verbruikt de trigger de code bij de eerste `last_sign_in_at`.
- **Onbevestigde gebruikers met een tikfout-adres** blijven in `auth.users` staan, met een profiel zonder naam. Ze hebben nooit een sessie gehad. Opruimen valt buiten deze taak.
- **Foutmeldingen van GoTrue:** een `raise` in de trigger komt terug als een algemene 500 ("Database error saving new user"). De client controleert daarom eerst via `check_invite` en vertaalt die algemene fout ook naar "Deze code is niet geldig.". Een 500 mag de verbindingsbanner niet tonen; dat klopt met de bestaande regel (alleen netwerkfout, 502, 503 en 504).
- **`check_invite` is publiek** en kan dus gebruikt worden om codes te raden. Codes moeten daarom lang en willekeurig zijn: minstens 10 tekens uit een alfabet zonder verwarrende tekens. Het formaat ligt vast bij het aanmaken in de beheerderstaak. Hier volstaat dat de functie alleen ja of nee teruggeeft. Die taak moet dit formaat respecteren.
- **Templates in de cloud:** `config.toml` geldt alleen lokaal. Bij uitrol moeten de Nederlandse templates (met `{{ .Token }}`) ook in het cloud-project gezet worden. Anders bevat de mail in productie geen code.
- **Welke template Supabase gebruikt:** een nieuwe gebruiker krijgt de bevestigingsmail, een bestaande de inloglinkmail. Beide moeten link én code bevatten; criterium 6 test daarom beide gevallen.
- **Verlopen code testen:** het veld voor het verzendtijdstip verschilt tussen GoTrue-versies (`confirmation_sent_at`, `recovery_sent_at` of `auth.one_time_tokens`). De tester controleert dit bij de vastgelegde CLI-versie. Lukt terugzetten niet betrouwbaar, dan draait die ene test met een aparte, korte `otp_expiry`.
- **Snelheidslimieten:** `email_sent`, `max_frequency` en `token_verifications` kunnen tests laten mislukken die veel mails sturen. Lokaal verhogen; in de cloud bewust laten staan.
- **Bestaande tests:** `createTestUser` gaat nu door de trigger. Zonder code faalt elke bestaande databank- en e2e-test. Ook de oude gebruikers in de lokale databank vragen een `supabase db reset`.
- **Eerste beheerder:** zonder publiek scherm heeft de eerste gebruiker ook een code nodig. Die maak je met SQL in de databank aan. Het instellen als beheerder valt buiten deze taak.
- **Opengelaten door de requirement, zelf ingevuld** (in `docs/beslissingen.md`):
  - de naam wordt pas na de eerste bevestiging gevraagd, op een apart scherm;
  - de naam wordt getrimd;
  - de datumnotatie is "1 november 2026";
  - de melding bij een onbekend adres zonder code;
  - een weergavenaam hoeft niet uniek te zijn en kan in deze taak niet gewijzigd worden.
